# Database Design: Customer Registration

The persistence design for US-001. The conceptual model and its mapping to the
business language and the API contract are in the paired
`docs/designs/database/US-001-entity-model.md`; this document states the schema,
every constraint, the access paths, the transaction and error behavior, the
migration intent, and the sensitive-data rules.

This Story carries the project's **first** datasource, model and migration:
`prisma/schema.prisma` is a two-line placeholder today with no `datasource`,
no `generator` and no model.

## Model

One model, `User`, mapping to table `user` (PC-5).

| Prisma field | Column | Column type | Null | Constraint / default | Source |
|---|---|---|---|---|---|
| `id` | `id` | `uuid` | NOT NULL | Primary key. Value generated by the client from `@default(uuid())`; **the column carries no database default** | PC-3, PC-4 |
| `email` | `email` | `varchar(254)` | NOT NULL | `UNIQUE` | FR-2, BR-1, VR-3; PC-4 |
| `passwordHash` | `password_hash` | `text` | NOT NULL | none — deliberately unbounded | FR-10, SR-4; PC-10 |
| `role` | `role` | enum `Role` | NOT NULL | default `CUSTOMER` | FR-3; SC-2 |
| `createdAt` | `created_at` | `timestamptz(3)` | NOT NULL | default `now()` | FR-5; PC-6 |
| `updatedAt` | `updated_at` | `timestamptz(3)` | NOT NULL | maintained by Prisma's `@updatedAt` | PC-6 |

Enum `Role`, one value: `CUSTOMER`. The business glossary types `User.role` as an
enum and SC-2 defines `CUSTOMER` as the default and only role, so the enum
carries exactly one member. Adding a second is `ALTER TYPE … ADD VALUE`, which
is additive; that is the Story that introduces the role, and this design adds
nothing on its behalf.

The Prisma model shape above was checked against the installed toolchain rather
than asserted: `npx prisma validate` accepts it on Prisma 7.10.0.

### Why each column type is what it is

**`id` is a native `uuid`, not `text`.** PC-3 fixes the strategy —
`String @id @default(uuid())` — and leaves the storage type open. PC-4 requires
`@db.VarChar(n)` "or an equivalent explicit type" for every bounded text column,
and a UUID is bounded; `@db.Uuid` is that equivalent explicit type. It is also
the stronger choice: the database itself rejects a malformed value, and 16 bytes
beats a 36-character string in every index that touches it. Prisma still surfaces
the value to application code as a `string`, which is what the API contract
declares (`format: uuid`, AC-11, PC-3). Leaving it as the implicit `text` would
be the one column in the table with no declared type, which is exactly what PC-4
exists to prevent.

**`email` is `varchar(254)`.** The same number as the Zod bound at the boundary,
which is the point: VR-3 requires them to match so that an over-long address
fails as a `400` at the boundary rather than as a database error, and a mismatch
between them — or an unbounded column — is a PC-4 violation. 254 is the longest
address SMTP can carry.

**`password_hash` is unbounded `text`, and this is the one exemption.** PC-10
states it directly and gives the reason: the encoded Argon2id hash's length
follows the SC-1 cost parameters, so a bound set today silently truncates after a
parameter change. PC-10 also says any *other* exemption from PC-4 needs an
approved decision; this design takes none.

**Timestamps are `timestamptz(3)`, declared explicitly.** PC-6 requires
`timestamptz` in UTC. Prisma's default mapping for `DateTime` on PostgreSQL is
`timestamp(3)` **without** a time zone, so the annotation is not decoration —
omitting it produces a column that violates PC-6 while the schema still looks
correct. Precision `(3)` is milliseconds, which is what AC-11's serialization
example carries (`2026-09-01T08:15:30.000Z`), so the wire format and the stored
value agree to the digit.

### Naming

Per PC-5: model `User` → table `user`; `passwordHash` → `password_hash`,
`createdAt` → `created_at`, `updatedAt` → `updated_at` via `@map`. `id`, `email`
and `role` need no mapping — the two names already agree.

The primary-key and unique-constraint names are left as Prisma generates them,
which PC-5 permits ("keep Prisma's generated names unless a review requires an
explicit one"). The enum type name is likewise left as Prisma generates it:
PC-5's snake_case rule is written for models and fields, and this design does not
extend a rule beyond what it says.

## Constraints

| Constraint | On | Enforces | Source |
|---|---|---|---|
| Primary key | `user.id` | Row identity | PC-3 |
| `UNIQUE` | `user.email` | One account per email address, at the database level | BR-001, BR-1; PC-4 |
| `NOT NULL` | every column | No attribute of this model is optional | PC-4 |

Every column is non-null. PC-4 permits `?` only where the design says a value may
be absent, and none may: an account with no email could not be logged into, one
with no hash could not be authenticated, and the role and both timestamps have
defaults.

**The unique constraint is not a duplicate of the service check — both are
required.** BR-1 says so explicitly and PC-4 gives the reason: an
application-level check alone cannot stop a race. See Concurrency below, which is
where this stops being a formality.

## Indexes

| Index | Origin | Access path that justifies it |
|---|---|---|
| Primary key on `id` | Implicit | Lookup by id, which US-003 will use for `/api/v1/users/me`. Nothing in US-001 reads by id |
| Unique index on `email` | Implicit, from the `UNIQUE` constraint | The uniqueness check on the registration path (BR-1), and the login lookup US-002 adds — PC-7 names it as the first example |

**No index is added beyond these two, and none is added by hand.** PC-7 requires
an index for every column a repository filters on, and forbids adding a
duplicate where a `@unique` constraint already provides one. `email` is the only
filtered column in this Story and it already has an index for a different reason.
There is no foreign key to index, because there is no relation.

## Access paths

Two queries, both in `src/modules/users/users.repository.ts` — the only file
with Prisma access to this record, because `users` owns it (BR-6, AD-2, PC-1).

| # | Operation | Shape | Selects | Source |
|---|---|---|---|---|
| 1 | Uniqueness check | `findUnique` by `email` | `id` only — existence is the whole question | BR-1, PC-8 |
| 2 | Insert | `create` | `id`, `email`, `role`, `createdAt` — exactly the four the response carries | FR-5, PC-8, SR-5 |

Both accept an optional transactional client and neither opens a transaction of
its own (PC-9).

**Neither query selects `password_hash`.** PC-8 requires selecting only what is
needed and singles out this column: a query that reads a user row must not select
it unless the caller is the authentication path that needs it. Registration is
not that path — it writes the hash and never reads one. Selecting the four
response fields on the insert is what makes SR-4 structural rather than a promise
about a mapper downstream: the hash never leaves the repository on this route.

**No unbounded query exists.** There is no `findMany` in this Story and no list
endpoint (PC-8; AC-8's pagination strategy stays untouched).

## Transaction and concurrency

**The write is one transactional operation, opened by `users.service.ts`** — the
service that owns the record — and composed of access paths 1 and 2 above
(BR-5, BR-6; PC-9, AD-3). `auth` reaches it through that service and has no
repository for a record it does not own.

**The transaction gives atomicity. It does not, by itself, prevent the race.**
This is the load-bearing point of the design and is worth stating plainly rather
than leaving to be discovered: under PostgreSQL's default READ COMMITTED
isolation, two concurrent registrations for the same email can both find no
existing row and both proceed to insert. One commits; the other fails on the
unique constraint. That is precisely why BR-1 requires the constraint *and* the
check, and why PC-4 says an application-level check alone is not sufficient.

So the design's answer to EC-3 has three parts:

1. the check catches the ordinary duplicate cheaply and without hashing a
   password (FR-7, SC-3's decision against equalizing registration timing);
2. the unique constraint catches the racing duplicate, which the check cannot;
3. **the constraint violation is translated into the same failure the check
   produces** — `ConflictError('EMAIL_ALREADY_REGISTERED')` — so that the two
   paths are indistinguishable to a client, which is what the Specification's
   Error Handling table and the API contract's `409` both require.

Point 3 is a persistence-design obligation, not an implementation detail: Prisma
raises the unique violation as `PrismaClientKnownRequestError` with code `P2002`,
and it must be caught where Prisma is visible — in the repository or in the
service that called it — and converted. Two things must not happen to it. It must
not reach the centralized error middleware as a Prisma error, because AD-6 maps
`ZodError` and `DomainError` only and would return a generic `500` for a case the
contract declares as `409`. And nothing from it may reach the response body or a
log line: not the Prisma message, not `P2002`, not the constraint name. SC-9's
list is authoritative on that and SR-6 applies it to exactly this path.

**No isolation level is raised, and none may be inferred.** READ COMMITTED plus
the unique constraint is the design; SERIALIZABLE would add retry handling and
contention for an invariant a constraint already enforces exactly. A Story that
needs a different level raises it as its own decision.

## Sensitive data

| Column | Rule | Source |
|---|---|---|
| `password_hash` | Argon2id hash only. Never plaintext, never logged, never returned by any endpoint, never selected on a read path that is not authentication | FR-10, SR-3, SR-4; SC-1, PC-10 |
| `email` | Personal data. Persisted and returned to its own owner on registration. **Never written to an audit log line** — SC-9's decided audit-event content is `event`, `userId`, `requestId` and no personal data, and FR-12 states the same. The address stays recoverable through `userId` when an investigation needs it | FR-12; SC-9 |

No other column is sensitive. Nothing in this model requires encryption at rest
beyond what the deployment provides, and this design does not introduce a
requirement for one.

The plaintext password is not a column, an attribute, or a value this model ever
sees — it exists only in the inbound request body (SR-3).

## Schema initialization and migration intent

### Schema file

`prisma/schema.prisma` gains, for the first time:

- a `datasource` block, provider `postgresql`;
- a `generator` block;
- the `Role` enum and the `User` model above.

### Migration

One migration, created with `npm run prisma:migrate` and committed in the same
change (PC-2). Its intent:

1. `CREATE TYPE` for the `Role` enum with the single value `CUSTOMER`;
2. `CREATE TABLE "user"` with the six columns, their types and their NOT NULLs
   as tabled above, `created_at` defaulting to `now()` and `role` defaulting to
   `CUSTOMER`;
3. the primary-key constraint on `id`;
4. the unique constraint on `email`, and the index PostgreSQL creates with it.

It is purely additive. Nothing is dropped or narrowed, so PC-2's
destructive-migration rule and SC-8's recorded-human-decision requirement do not
apply. The migration name is left to the implementer; PC-2 and PC-5 prescribe
none.

`id` has **no database-level default**. Prisma's `@default(uuid())` generates the
value in the client, so the migration must not be read as producing a
`gen_random_uuid()` column default, and a row inserted by raw SQL outside Prisma
would need to supply its own id. Nothing in this Story does that; it is recorded
because the migration file will not say it.

### Prisma 7 changed how the connection is configured — read this before planning

Two facts about the installed toolchain were verified during this stage and are
not what `persistence-conventions.md` PC-1's wording leads a reader to expect.
Both land on `IMPLEMENTATION_PLANNING`, and one needs a human decision.

**1. The `datasource` block can no longer carry `url`.** On Prisma 7.10.0,
`url = env("DATABASE_URL")` in the schema is a validation error (P1012):
*"The datasource property `url` is no longer supported in schema files. Move
connection URLs for Migrate to `prisma.config.ts`."* Running
`npx prisma migrate status` against a schema without it then reports:
*"The datasource.url property is required in your Prisma config file when using
prisma migrate status."* So the Story must add a `prisma.config.ts` carrying the
migration connection URL. Verified by running both commands; the exact
TypeScript shape of that file was not executed here and should be confirmed
against the installed version when it is written.

That file has to read `DATABASE_URL` from the environment, which meets
`AGENTS.md`'s flat rule that `process.env` is read only in `src/config/env.ts`
(AD-7). The lint rule that enforces AD-7 is scoped to `files: ['src/**/*.ts']`
in `eslint.config.js`, so a root-level `prisma.config.ts` would pass `npm run
lint` while contradicting the prose — the same position `scripts/` is already in.
Which way to resolve it is not this stage's call: either the config file reads
the variable directly and AD-7's wording is narrowed to `src/`, or it imports the
validated value from the configuration boundary. `IMPLEMENTATION_PLANNING` should
settle it deliberately rather than let the lint's silence decide.

**2. `PrismaClient` requires a driver adapter, and that dependency is approved
and installed.** In the installed `@prisma/client` 7.10.0,
`PrismaClientOptions` is a union of exactly two shapes: one requiring
`accelerateUrl` (Prisma Accelerate) and one requiring `adapter`, documented in
the type as *"A driver adapter is **required** unless you connect to your
database through Prisma Accelerate."* The official PostgreSQL adapter is
`@prisma/adapter-pg`, and `src/lib/prisma.ts` has no working form without it.

**Revision 1 of this document recorded that adapter as absent and as an
unapproved new dependency requiring a decision at `HUMAN_PLAN_APPROVAL`. That is
no longer true**, and design review v1 `d-3` is the finding that says so. Commit
`0339b4a` (author `KShust`, 2026-09-02) adds `@prisma/adapter-pg` pinned to
`7.10.0` and records the SC-6 approval and its reason in the commit message.
Re-verified during this re-run: `@prisma/adapter-pg` 7.10.0 is declared in
`package.json` and installed, and its `pg` 8.23.0 driver arrives transitively.

Two consequences follow. **`IMPLEMENTATION_PLANNING` must not carry the adapter
to `HUMAN_PLAN_APPROVAL` as an open decision** — it cites `0339b4a` as the
approval that already exists. And nothing above changes either way: the model,
its constraints, its indexes and its access paths never depended on which driver
carries the connection, which is why this correction is a documentary one and
the persistence design is unrevised.

**PC-1 itself should be revisited by whoever owns that decision.** It says the
connection string "comes from `DATABASE_URL` … parsed and validated in
`src/config/env.ts`", which is still true of the application, and that "exactly
one `PrismaClient` instance exists, exported from `src/lib/prisma.ts`", which is
also still true. What it does not describe — because it predates Prisma 7 — is
that the client now needs an adapter object and that migrations read their URL
from a separate config file. Amending a convention document is not this stage's
to do; it is recorded so the amendment is a decision rather than a drift someone
notices later.

### Test database

PC-1's test-database setup is required by this Story (FR-19) and is specified in
PC-1 in full: a `docker-compose.yml` `db` service on port 5433, `.env.test` with
its own `DATABASE_URL`, `prisma migrate deploy` against an empty database from a
Vitest `globalSetup`, truncation between tests, serial execution for
`tests/integration`, and a `services: postgres` block in CI. This design adds
nothing to that list and narrows nothing in it.

One consequence of the model belongs here: the truncation fixture has exactly one
table to clear, `user`. Because the row is the whole of a Customer's persisted
state, truncating it is sufficient to isolate one test from the next — there is
no dependent table to cascade to and no sequence to reset, since `id` is a
client-generated UUID rather than a serial.

## Traceability

| Requirement | Where this design satisfies it |
|---|---|
| FR-2 (exactly one `User` per email) | Unique constraint on `email` + the service check, as one transactional operation |
| FR-3 (role `CUSTOMER`) | `role` column, enum `Role`, default `CUSTOMER` |
| FR-4 (enabled, with no state column) | No account-state column; the row's existence is the state |
| FR-5 (four-field response) | Insert selects exactly `id`, `email`, `role`, `createdAt` |
| FR-10 (Argon2id hash only) | `password_hash`, non-null, unbounded, never selected on this path |
| BR-1 (two-place uniqueness) | Service check + database constraint, with the P2002 translation |
| BR-2 / VR-4 (normalization) | The normalized value is what is stored, so the constraint compares what the application compared |
| BR-5 (transactional read-then-write) | One `prisma.$transaction` opened by `users.service.ts` |
| BR-6 (`users` owns the record) | Both access paths live in `users.repository.ts`; `auth` reaches them through `users.service.ts` |
| VR-3 (254 bound on both sides) | `varchar(254)`, the same number as the Zod bound |
| EC-3 (concurrent duplicates) | Constraint catches the race; the violation becomes the same `409` |
| EC-8 (over-long email) | Boundary rejects at 254 before the database sees it; the column agrees |
| NFR-004 (explicit constraints, committed migration) | Every column's type, nullability and constraint stated; one additive migration |

AC-005 and AC-006 are satisfied at the model level by `password_hash` never being
selected and never appearing in a response DTO. AC-007 is not a persistence
concern — the audit event is a log line, and the only thing this design owes it
is that the email is not part of it.

## Findings recorded for later stages

None of these blocks `DESIGN_REVIEW`, and none is an entry in
`docs/decisions/US-001-open-decisions.md` (all twelve of which are `RESOLVED` at
v7). Each is stated in full above and summarized here so it is not lost.

1. **`@prisma/adapter-pg` is approved and installed — no longer a finding, and
   recorded only so the revision-1 version of it is not acted on.** Revision 1
   called it an unapproved dependency needing a decision at
   `HUMAN_PLAN_APPROVAL`; commit `0339b4a` approved and added it under SC-6
   before this revision, as design review v1 `d-3` observed.
   `IMPLEMENTATION_PLANNING` cites that commit instead of carrying the question
   to the gate.
2. **`prisma.config.ts` must read `DATABASE_URL`**, which the letter of AD-7
   assigns to `src/config/env.ts` alone while the lint rule enforcing it covers
   only `src/**`. `IMPLEMENTATION_PLANNING` should choose a resolution
   deliberately.
3. **A database-level normalization constraint was considered and not
   specified.** PC-4 says a business invariant expressible as a database
   constraint is expressed as one, and BR-2's "trimmed then lowercased" could be
   a `CHECK (email = lower(btrim(email)))` that would stop a future writer from
   inserting an unnormalized address past the boundary. It is not specified here
   for two reasons: no requirement asks for it, and Prisma's schema language
   cannot express a `CHECK`, so it would have to be added as raw SQL in the
   migration and would then sit outside the schema Prisma reconciles against.
   Recorded so `DESIGN_REVIEW` can disagree with the judgement rather than have
   to notice the question.
